# 架构说明

## 目标

这是一个面向四位好友的私有麻将桌。架构的首要目标是**规则可验证、状态只有一个权威来源、部署简单**，而不是支撑公开匹配或高并发。因此项目保持单进程、单数据库，不引入 ORM、消息队列、WebSocket 服务、微服务或独立前端框架。

## 分层

```text
微信小程序页面（lobby / table / replays / verify）
        │
        ├── room-state.js       页面状态保护、中文错误、选牌动作
        ├── presentation.js     领域状态 → WXML 视图模型
        ├── layout.js           牌桌几何与响应式布局计算
        ├── cosmetics.js        角色、表情、互动道具的共享定义
        └── api.js              wx.request / 登录 / 长轮询 / 文件导入导出
        │
        ▼  HTTP JSON
server/http.js                  传输层：路由、鉴权、限流、长轮询、静态文件
        │
        ▼
server/service.js               应用层：房间流程、指令幂等、权限、结算落库
        │
        ├── server/bots.js      单人测试房的机器人决策与自动操作决策
        ├── miniprogram/lib/*   共享纯规则：牌、胡牌、洗牌、引擎、回放验证
        └── server/store.js     SQLite 持久化：用户、会话、房间、对局、历史
```

`miniprogram/lib` 不是普通的前端工具库，而是**服务端和小程序共用的纯业务核心**。它不访问 `wx`、HTTP 或数据库，因此服务端可以用它执行权威规则，客户端也可以用同一份代码做本地回放和牌山验证。浏览器试玩页按需加载这些模块。

## 各层职责

| 层 | 文件 | 职责 | 不应该做的事 |
| --- | --- | --- | --- |
| 纯业务核心 | `miniprogram/lib/tiles.js`、`rules.js`、`shuffle.js`、`engine.js`、`replay.js` | 牌编号、胡牌判定、计分、确定性洗牌、状态机、回放重建 | 读写数据库、发网络请求、依赖 `wx` 全局对象 |
| 共享展示定义 | `miniprogram/lib/cosmetics.js`、`layout.js` | 角色/表情/互动道具白名单、牌桌几何和视角计算 | 保存房间状态、决定动作合法性 |
| 页面适配 | `miniprogram/pages/` | 生命周期、`setData`、触控、页面跳转和本地播放状态 | 自己实现规则或直接改服务端快照 |
| 页面状态工具 | `miniprogram/lib/room-state.js` | 单调 revision 保护、可展示错误文案、可出牌动作查找 | 请求接口、保存房间状态 |
| 视图适配 | `miniprogram/lib/presentation.js` | 将服务端房间视图转换为固定 WXML 结构 | 修改规则状态 |
| 机器人策略 | `server/bots.js` | 单人测试的机器人决策和玩家自动操作决策 | 绕过 `engine` 的合法性检查或另写一套规则 |
| 客户端传输 | `miniprogram/lib/api.js` | 微信登录、HTTP 请求、长轮询取消、承诺码留存、导入导出 | 校验胡牌或计算结算 |
| 服务端传输 | `server/http.js` | 路由、请求体限制、鉴权、频率限制、长轮询连接管理和静态资源 | 实现业务规则 |
| 应用服务 | `server/service.js` | 房间/对局用例、权限、指令去重、事务、公开视图、社交与机器人推进 | 信任客户端结果、返回隐藏牌 |
| 持久化 | `server/store.js` | 参数化 SQL、JSON 快照读写、事务、历史裁剪 | 业务判断 |

## 关键数据流

1. 客户端游戏动作通过 `POST /api/rooms/:code/commands` 提交，并携带客户端当前看到的 `expectedRevision` 与唯一 `id`。四人全部准备时，服务端在最后一个准备指令中直接创建对局，不需要房主再点开始。
2. `http.js` 只做鉴权与转发；`service.command` 检查座位、revision、幂等回执和阶段，再由共享 `engine.act` 执行规则。
3. 服务端先写对局快照、房间快照、历史引用，再返回公开视图。`view()` 对当前玩家隐藏其他玩家的手牌、牌墙和种子。
4. 房间 revision 递增后触发 `EventEmitter`，挂起的 HTTP 长轮询返回最新公开视图。客户端页面用 `acceptRoom` 防止旧响应覆盖新状态。
5. 开局后进入 `commit` 阶段：服务端广播牌山校验码，四名客户端的牌桌页各自保存校验码并自动发送 `ack`。只有四人确认后才发牌；确认指令允许基于同一旧 revision 并发提交，避免四个人互相 409 重试。
6. 已结束小局公开完整牌谱。客户端用同一个 `engine` 和 `replay` 在本地重放验证，不需要服务端给出“验证通过”。
7. 角色、表情和互动道具走独立端点，只写入 `rooms.data` 并触发同一房间的 revision/长轮询；它们不进入对局命令、支付事件或回放。互动额度按当前 `matchId + handNo` 隔离，避免旧牌局请求消耗新牌局额度。
8. 单人测试房由 `service.advanceAutomatic` 驱动：机器人只通过 `botAction` 生成普通 `gameCommand`，自动操作也走同一命令校验、幂等和结算路径。

## 数据模型

- `rooms.data`：一个 JSON 房间快照，包含座位、准备状态、外观、表情、互动事件/额度、自动操作偏好、测试房机器人、当前对局 ID、revision 和操作回执。
- `matches.data`：一个 JSON 对局快照，包含设置、座位、累计分数、各小局完整命令/事件/结算与已完成牌谱。
- `users` / `sessions` / `history`：关系表，只保存账号、会话摘要和历史保留关系。
- 不把每张牌拆成数据库行。单局牌数量有限，JSON 快照能让一次指令的读取、校验、写回保持原子和可回放。房间社交状态与对局状态分列存储，避免表情或互动污染牌谱。

## 精简约束

- **单一权威服务**：所有规则与结算在服务端执行；客户端验证器只用于审计，不参与授权。
- **单一状态来源**：页面只缓存服务端房间视图；本地状态仅用于选牌、播放进度、展开面板等 UI 细节。
- **一次请求一个用例**：不引入通用状态管理库；重复的 revision 检查与错误处理集中在 `room-state.js`。
- **无运行时 npm 依赖**：服务端使用 Node 内置 HTTP、Crypto、SQLite；原生小程序使用自身框架。
- **验证与游戏共用核心**：避免服务端和客户端各写一套规则导致牌谱无法复核。
- **长轮询优先**：好友局人数和频率有限，长轮询比 WebSocket 网关更容易部署、恢复和调试。
- **社交与规则隔离**：角色、表情和互动只改变房间展示状态；对局快照、支付和回放不依赖这些美化数据。
- **机器人不享有规则特权**：单人测试中的机器人和自动操作仍调用同一个 `engine`，因此其动作可被同一套回放验证。

HTTP 端点、请求字段、幂等和长轮询协议见 [API.md](API.md)；规则、洗牌字节协议和发布验收标准见 [GOAL.md](../GOAL.md)。

## 扩展原则

- 新增规则优先改共享业务核心，并补纯规则/回放测试；不要在小程序页面里兜底规则。
- 新增 HTTP 能力时，传输层只解析输入、鉴权和选服务方法；业务状态转换放进 `service.js`。
- 新增持久化字段时，优先确认是否能放在已有 JSON 快照中；只有需要跨房间查询或并发索引时才加表。
- 若未来需要公开匹配、大量房间或水平扩展，再拆分 `service` 和 `store`；当前规模不需要为那时预付复杂度。
